# Проверка порядка Data Log

Дата: 31 октября 2026 года, около 01:54, Asia/Yerevan. Исследованная установка: PowerChute Serial Shutdown Agent 1.4.0.301 / Back-UPS BX1600MI из спецификации проекта.

Проверялся только `POST /ajaxdatalog` в отдельной авторизованной HTTP-сессии. Экспортер был остановлен на время прямых запросов и восстановлен после завершения; настройки ИБП и содержимое журналов не изменялись. Учётные данные, cookies, токены и полные ответы в этот документ не сохранялись.

## Подтверждено

- Прочитан весь доступный журнал: **2078 строк, 21 страница по 100 строк**.
- Timestamp каждой следующей строки меньше предыдущего, включая границы страниц. Повторяющихся timestamp нет.
- Глобальный максимум находится в первой строке первой страницы: **2026-10-31 01:37:46 +04:00**.
- Последняя строка: **2026-10-01 02:11:57 +04:00**.
- Выполнены 12 сравнений пагинации с полным эталонным обходом. Проверены размеры 1, 10, 25, 50 и 100; смещения 0, 1, 9, 10, 25, 50, 99, 100 и последние пять строк журнала. Каждая выборка совпала с ожидаемым срезом.
- Повторное чтение первой страницы после проб вернуло тот же порядок и total.
- Явные параметры DataTables `iSortingCols=2`, `iSortCol_0=0`, `iSortCol_1=1`, `bSortable_0=true`, `bSortable_1=true`, а также `sSortDir_0` / `sSortDir_1` со значениями `asc` и `desc` **не изменили ответ**: в обоих случаях вернулись новые записи первыми. На эти параметры как на переключатель порядка полагаться нельзя.

Первые три timestamp эталона:

```text
2026-10-31T01:37:46+04:00
2026-10-31T01:17:46+04:00
2026-10-31T00:57:46+04:00
```

Этого наблюдения достаточно, чтобы использовать существующий `ordering: newest_first` для проверенного порядка текущей установки: первая страница содержала глобально самую новую запись. Проверка упорядоченности первой страницы в самом адаптере сохраняется. Для других версий и после изменений поведения API порядок нужно проверять отдельно.

```yaml
datalog:
  ordering: newest_first
  page_size: 10
```

## Граница проверки

После эталонного обхода экспортер увидел очередную штатную запись с timestamp **2026-10-31 01:57:46 +04:00**. Дополнительная прямая API-проверка, что новая строка вставилась в начало и сдвинула прежние строки, не выполнялась: запрос Windows UAC был отменён. Наличие этой записи через полный обход экспортера само по себе не доказывает её позицию на странице.

Установленный конфиг в рамках исследования не менялся: рабочий экспортер остался в режиме `scan` с `page_size: 100`.

## Повторная проверка

Опциональные интеграционные тесты находятся в `internal/powerchute/live_ordering_test.go`:

- `TestLiveDataLogOrdering` выполняет полный обход, проверки срезов и запросы `asc` / `desc`. При `POWERCHUTE_ORDERING_REPORT` сохраняет JSON только с timestamp и результатами проверок.
- `TestLiveDataLogInsertionAtHead` запускается после появления новой записи, сверяет её с сохранённым эталоном и проверяет production-адаптер `newest_first`. Для сохранения результата можно задать `POWERCHUTE_INSERTION_REPORT`.

Обычный `go test ./...` пропускает их. Для подключения нужны `POWERCHUTE_LIVE_TEST=1`, явный абсолютный `POWERCHUTE_CONFIG` и отсутствие другой активной сессии этого пользователя PowerChute. Защищённый установленный конфиг Windows требует повышения прав. До теста остановите экспортер, после теста запустите его обратно; тесты закрывают только созданную ими сессию.
